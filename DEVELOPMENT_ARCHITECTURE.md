# Price Watcher — технический план новой разработки

Документ описывает архитектуру новой версии. Это план, а не описание уже реализованного. Правила работы ИИ-разработчика вынесены в `AGENTS.md`, состояние функций — в `FEATURE_STATUS.md`.

## 1. Где что работает

| Узел | Что на нём |
|---|---|
| Домашний узел (Raspberry Pi) | Сайт, API, PostgreSQL, планировщик, worker с парсером и браузером, Caddy с сертификатом HTTPS |
| Арендный хост (VPS) | Telegram-бот, сторож, пересылка порта 443 в туннель, хранилище зашифрованных копий |

Сайт работает дома, но в интернет смотрит арендный хост. Между хостом и Raspberry Pi поднят туннель WireGuard, который Raspberry Pi устанавливает сама. Хост пересылает зашифрованный поток порта 443 в туннель, не раскрывая его (режим TCP, без расшифровки). HTTPS расшифровывает Caddy на Raspberry Pi; сертификат и его закрытый ключ хранятся только дома.

Что видит и хранит арендный хост:

- видит только факт соединения, IP посетителя и объём трафика; содержимое запросов, пароли и cookie ему недоступны;
- хранит ключи туннеля, токен Telegram-бота, chat id администраторов и зашифрованные копии без ключа шифрования;
- данные сайта, базу и сертификат не хранит.

Правила, которые делают хост заменяемым:

- Raspberry Pi подключается к хосту по доменному имени (`tunnel.<домен>`), не по IP, и заново разрешает имя при обрыве туннеля.
- Переезд на другой хост: развернуть тот же Compose с сохранёнными ключами и поменять IP в DNS. На Raspberry Pi ничего не меняется.
- Конфигурация и ключи хоста входят в резервную копию.
- Хост передаёт настоящий IP посетителя по PROXY protocol; Caddy на Raspberry Pi принимает его только из туннеля. Без этого не работают ограничения попыток входа по IP.
- Сертификат Caddy получает по проверке TLS-ALPN, которая проходит сквозь пересылку; доступ к DNS-записям для этого не нужен.

Что это даёт:

- не нужны белый IP от провайдера и проброс портов на роутере;
- домашний адрес не виден снаружи, роутер закрыт;
- запросы в магазины по-прежнему идут с домашнего IP.

Требования к домашнему узлу:

- Компьютер x86-64 с 8 ГБ памяти и больше (мини-ПК): PostgreSQL и браузер работают одновременно. Raspberry Pi не подходит: worker использует установленный Google Chrome, а Chrome для Linux выпускается только под x86-64 (решение 06.10.2026, см. раздел 7).
- Система и база на SSD, не на карте памяти: карта от постоянной записи выходит из строя.
- Источник бесперебойного питания желателен: при отключении света или домашнего интернета сайт недоступен.

Worker может работать и на домашнем ПК: он общается с API по тому же протоколу (раздел 8).

Переносимость: проект запускается на macOS, Windows и Linux, не только на Raspberry Pi. Если домашний узел вышел из строя, сайт временно поднимается на другом компьютере и разворачивается из резервной копии (раздел 11). Поэтому код не зависит от системы: ввод и вывод процессов — UTF-8 независимо от кодировки системы, файлы читаются и пишутся в UTF-8 явно, часовой пояс — из пакета tzdata. CI прогоняет полный набор тестов на Linux и на Windows.

Взаимный контроль:

- Бот раз в минуту опрашивает API через туннель. Нет ответа 3 минуты — бот сам пишет администраторам в Telegram: токен и chat id администраторов лежат в его конфигурации.
- Worker раз в минуту шлёт heartbeat в API. Молчит дольше 5 минут — администраторы получают уведомление.
- Каждый опрос бота обновляет `service_heartbeats`. Бот молчит дольше 5 минут — API создаёт уведомление в колокольчике администраторов.
- На каждое событие приходит и сообщение о восстановлении.

## 2. Стек

- **Python 3.13** — API, планировщик, worker, бот.
- **FastAPI + Pydantic** — HTTP API и схемы.
- **PostgreSQL** — единственный источник истины и очередь заданий.
- **SQLAlchemy 2 + Alembic** — доступ к базе и миграции.
- **Jinja2 + HTML + CSS + обычный JavaScript** — сайт. Сервер рендерит и страницы, и HTML-фрагменты для частичного обновления. JS не собирает карточки из JSON и не форматирует деньги.
- **patchright + Google Chrome** — на worker, для магазинов за защитой от ботов: Playwright с закрытыми признаками управляемого браузера, Chrome с окном (на сервере — Xvfb).
- **Docker Compose** — изоляция сервисов; образы собираются под arm64 (Raspberry Pi, Mac на Apple Silicon) и amd64 (обычные ПК и ноутбуки).
- **Caddy** на домашнем узле — HTTPS. **WireGuard + пересылка TCP** на арендном хосте — туннель без расшифровки трафика.
- **`logging` в JSON** — структурированные логи.
- **pytest** — unit, integration, contract, security; Playwright — UI-сценарии сайта.
- **import-linter** — автоматическая проверка границ модулей.
- **Swift 6 + SwiftUI** — приложение iPhone/iPad.

Версии закрепляются в lock-файлах и Docker-образах. Секреты — в `.env` на узле, в Git не попадают.

Отложено до работающего MVP: staging-окружение, метрики, APNs, серверный кэш. Вместо кэша — HTTP `ETag` на ответах чтения.

## 3. Модули

```text
Сайт ──────── cookie-сессия ─┐
iPhone/iPad ─ bearer-токен ──┴─> api ─> application ─> domain
                                           │
                                           └─> persistence ─> PostgreSQL
Worker ─ токен worker ─> api/worker   (взять задание / heartbeat / вернуть результат)
Бот ──── токен сервиса ─> api/internal (забрать уведомления / состояние узлов)
```

```text
src/pricewatch/
  domain/          сущности и правила расчётов; не импортирует ничего из проекта
  application/     сценарии; зависит только от domain и интерфейсов репозиториев
  persistence/     модели БД, репозитории, миграции
  api/             маршруты /api/v1, /web, /worker/v1, /internal/v1; аутентификация
  web/             шаблоны, фрагменты, CSS, JS
  parsers/         registry, общий парсер, адаптеры магазинов, нормализаторы
  worker/          клиент очереди на домашнем узле, запуск парсеров, загрузка картинок
  scheduler/       плановые запуски
  bot/             Telegram-бот и сторож
  observability/   логи, идентификаторы запросов и ошибок
  bootstrap/       сборка приложения: связывает сценарии с реализациями репозиториев
  config/          настройки процесса из окружения и .env
ios/PriceWatcher/  отдельный Xcode-проект
tests/  unit/ integration/ contracts/ security/ ui/
tools/  check_project_map.py, deps.py, import_contracts.py (свой тип контракта import-linter)
```

Направление зависимостей: `api → application → domain`; `persistence` реализует интерфейсы из `application`; адаптеры магазинов не импортируют друг друга; `worker` и `bot` не импортируют `persistence`.

`persistence` импортирует только `bootstrap`. Он создаёт репозитории и передаёт их сценариям при старте процесса. `api` и `scheduler` получают готовые сценарии от `bootstrap` и обратиться к базе в обход сценариев не могут. В `bootstrap` нет бизнес-логики и обработчиков.

`config` читают `api`, `bootstrap`, `worker`, `scheduler` и `bot`; `domain` и `application` его не импортируют — сценарии получают нужные значения параметрами.

`domain` импортирует только стандартную библиотеку Python. Любая сторонняя библиотека в `domain` запрещена; исключение добавляется только с согласия владельца.

Контракт «адаптеры не импортируют друг друга» добавляется вместе с первым адаптером на этапе 5; до этого он отмечен в карте как ожидающий. Эти правила записаны контрактами import-linter и проверяются в CI.

Бизнес-правила не размещаются в HTTP-обработчиках, шаблонах, Swift или конкретном парсере.

## 4. Пользователи, роли, вход

Одна база, у каждой пользовательской записи есть `user_id`. Каждый запрос фильтрует по владельцу на уровне репозитория; чужой идентификатор даёт `404`.

Роли:

| Действие | user | admin |
|---|---|---|
| Свои товары, категории, группы | да | да |
| Добавить ссылку на любой сайт (кроме отключённых администратором) | да | да |
| Ручной запуск проверки | нет | да |
| Расписание, пороги, магазины, приглашения | нет | да |
| Решения по подозрительным изменениям | нет | да |
| Технические ошибки в Telegram | нет | да |
| Колокольчик системных уведомлений | нет | да |
| Сводка проверки в Telegram | да | да |

Регистрация — по приглашению. Администратор создаёт одноразовую ссылку со сроком 7 дней; по ней открывается форма «Зарегистрироваться». Открытой регистрации нет: каждый пользователь может заставить парсер ходить по ссылкам. Первый администратор создаётся командой на сервере.

Логин — 3–64 символа: латиница, цифры, точка, дефис, подчёркивание; сравнивается без учёта регистра. Пароль — 10–128 символов и не совпадает с логином, без правил состава (NIST SP 800-63B).

Вход на сайт: логин и пароль (argon2id через argon2-cffi), серверная сессия в cookie `HttpOnly; Secure; SameSite=Lax`. Сессия живёт 30 суток с момента входа без продления; отметка последнего визита обновляется не чаще раза в час. Ограничение: 5 неудачных попыток на логин и 20 на IP за 15 минут; неудачи хранятся в `auth_failures`. Ответ при ошибке входа не уточняет, что неверно (`INVALID_CREDENTIALS`), а время ответа для несуществующего логина выравнивается проверкой фиктивного хеша. Смена пароля и отключение пользователя отзывают все его сессии и устройства.

Серверный ключ `PRICEWATCH_SECRET_KEY` (не короче 32 байт) — основа HMAC для всех кодов, токенов и сессий: в базе хранится только HMAC с этим ключом, поэтому перебор по копии базы без ключа бесполезен. Смена ключа разлогинивает всех — это осознанный аварийный рычаг.

Вход в приложение: pairing-код. Его генерирует сервер по кнопке на сайте после входа либо по команде боту от привязанного Telegram-аккаунта. Код — 8 символов из алфавита в 32 знака (A–Z, 2–7), живёт 5 минут, одноразовый. Неверный ввод не указывает, какой код перебирают, поэтому ограничение — не больше 10 неверных вводов с одного IP за 15 минут (`auth_failures`). В базе хранится только HMAC кода.

Refresh-токены:

- Ротация при каждом обновлении; токены одного устройства образуют семью: отзыв семьи — это отзыв устройства.
- Следующая пара выводится из предыдущего refresh-токена через HMAC с серверным ключом. Поэтому повтор предыдущего токена в течение 60 секунд возвращает ту же новую пару без хранения токенов в открытом виде. Так приложение не разлогинивается, если ответ потерялся в сети.
- Повтор за пределами окна отзывает всю семью и создаёт уведомление администраторам.
- Access-токен — случайная строка, живёт 15 минут; в базе её HMAC, срок и устройство, поэтому отзыв действует сразу. Refresh живёт 60 дней.

Два способа авторизации на одном API разделены жёстко:

- `/api/v1/*` принимает только `Authorization: Bearer`; cookie игнорируется, CSRF не требуется.
- `/web/*` принимает только cookie-сессию; заголовок `Authorization` игнорируется. Для изменяющих запросов обязательны CSRF-токен и совпадение `Origin`. CSRF-токен — HMAC токена сессии с серверным ключом: живёт столько же, сколько сессия, и не хранится.
- `/worker/v1/*` — только токен worker, `/internal/v1/*` — только токен сервиса.
- CORS разрешён только своему домену.

Telegram привязывается к пользователю одноразовым кодом с сайта.

## 5. Данные PostgreSQL

Имена полей в базе и в JSON — `snake_case`. Деньги — целые копейки (`*_minor`), только RUB. Иная валюта на странице даёт статус `UNSUPPORTED_CURRENCY`. `float` для денег запрещён.

Каталог ссылок общий, списки покупок — личные. Одна ссылка проверяется один раз, сколько бы пользователей её ни отслеживали.

Учётные записи и сессии:

- `users(id, login, password_hash, role, display_name, telegram_chat_id, categories_order_version, created_at, disabled_at)` — `categories_order_version` — версия порядка категорий пользователя.
- `invites(id, code_hash, role, created_by, created_at, expires_at, used_by, used_at)`
- `web_sessions(id, user_id, token_hash, created_at, last_seen_at, expires_at, revoked_at)`
- `devices(id, user_id, name, created_at, last_seen_at, revoked_at)` — устройство и есть семья refresh-токенов.
- `refresh_tokens(id, device_id, token_hash, issued_at, used_at, expires_at)` — отзыв через `devices.revoked_at`.
- `access_tokens(id, device_id, token_hash, issued_at, expires_at)`
- `pairing_codes(id, user_id, code_hash, created_at, expires_at, used_at)`
- `auth_failures(id, kind, subject, ip, created_at)` — неудачные попытки входа (`login`) и ввода кода (`pairing`) для ограничений.

Все `*_hash` здесь — HMAC-SHA256 с серверным ключом, пароли — argon2id.
- `idempotency_keys(user_id, key, request_hash, response_status, response_body, created_at)` — уникально `(user_id, key)`, срок 24 часа. Тот же ключ с другим телом запроса даёт `409`.

Личные данные пользователя (у каждой таблицы `user_id`, `version`, `deleted_at`):

- `categories(id, name, name_normalized, position, …)` — уникально `(user_id, name_normalized)` среди неудалённых.
- `groups(id, category_id, name, name_normalized, position, …)` — уникально `(category_id, name_normalized)`. Нормализация: обрезка пробелов, один регистр, `ё → е`. Опечатка в регистре или пробеле не создаёт дубль.
- `items(id, category_id, group_id, name, full_name, quantity, in_total, include_stale, position, …)` — товар в списке пользователя. `in_total = false` означает «только наблюдаю». `include_stale = true` — пользователь включил в итог товар с устаревшей ценой той же отметкой «в итоге»; сбрасывается, когда цена снова становится актуальной. Жизненный цикл: `state` (`active`, `purchased`, `archived`), для покупки — `purchased_at`, `purchase_price_minor` (цена за штуку), `purchase_store_id`, `purchase_quantity`, для архива — `archived_at`. Эти столбцы добавляются миграцией вместе с маршрутами товаров.
- `item_links(id, item_id, tracked_link_id, store_id, valid_from, valid_to)` — уникальна активная пара `(item_id, store_id)`. Связь не удаляется: замена и отключение ссылки закрывают её (`valid_to`), поэтому история цены товара сохраняется.

Общий каталог:

- `stores(id, canonical_host, display_name, color, has_card_price, parser_key, enabled, auto_created, fetch_method, min_delay_ms, paused_until, pause_level, pause_reason, created_at)` — `auto_created` — магазин создан сам из ссылки пользователя; `fetch_method` — способ, сработавший в прошлый раз (`http`, `browser`); пауза магазина после 403/429 или капчи — `paused_until` и ступень `pause_level`. Пауза между запросами по умолчанию: 2 с без браузера, 5–9 с в браузере, 60 с для Авито (решение 06.10.2026).
- `tracked_links(id, store_id, normalized_url, region_code, baseline_title, image_path, created_at)` — уникально `(normalized_url, region_code)`. Подтверждения администратором нет (решение 06.10.2026).
- `price_observations(id, tracked_link_id, task_id, checked_at, status, price_minor, card_price_minor, availability, title, region_code, confirmation, source)` — уникально `task_id`. `status` — `ok` или код ошибки сбора цен; `source` — откуда цена. История только дополняется.
- `price_decisions(id, observation_id, kind, decision, decided_by, decided_at)`

Очередь и служебное:

- `parse_runs(id, kind, slot_key, status, requested_by, total, done, failed, started_at, finished_at)` — `kind`: `scheduled`, `manual`, `on_add`.
- `check_tasks(id, run_id, tracked_link_id, status, priority, attempt, lease_until, heartbeat_at, worker_id, error_code, safe_message, duration_ms, created_at, finished_at)`
- `workers(id, name, token_hash, next_token_hash, last_seen_at, disabled_at)`
- `settings(key, value_json, version, updated_by, updated_at)`
- `notifications(id, user_id, channel, kind, dedup_key, payload_json, created_at, sent_at, attempts, read_at)` — `channel`: `telegram`, `in_app`.
- `service_heartbeats(service, last_seen_at)`
- `client_error_reports(id, user_id, device_id, app_version, os_version, screen, error_code, message, occurred_at, received_at)`
- `audit_events(id, actor_id, action, entity_type, entity_id, before_json, after_json, created_at)`

Все изменения схемы — миграциями Alembic. Партиционирование не вводится, пока объём этого не потребует.

### Конфликты правок

У изменяемых записей есть целое поле `version`. Клиент присылает версию, которую видел. Обновление выполняется одним запросом `UPDATE … WHERE id = … AND version = …`; ноль затронутых строк даёт `409 VERSION_CONFLICT` с актуальным состоянием. Перестановка присылает полный упорядоченный список идентификаторов и версию родителя: для товаров — версию группы, для категорий — `users.categories_order_version`.

### Удаление и отмена

Удаление товара, категории, группы и замена ссылки — мягкие: ставится `deleted_at`, ответ содержит `undo_token`. Интерфейс показывает «Отменить» 3 секунды. Сервер принимает отмену 15 секунд, чтобы медленная сеть не съела нажатие. Мягко удалённые записи стираются окончательно через 30 дней фоновой задачей.

## 6. Доменные правила

Регион один: Санкт-Петербург (`region_code = spb`, значение в настройках). Каждый адаптер выставляет город и проверяет его на полученной странице. Если город подтвердить нельзя, результат получает статус `REGION_MISMATCH` и в статистику не идёт.

**Действующая цена ссылки** — `card_price_minor`, если она есть, иначе `price_minor`.

**Ссылка участвует в расчётах**, если одновременно:

- магазин включён (`stores.enabled`);
- у неё есть успешное подтверждённое наблюдение, и по последнему такому наблюдению товар в наличии;
- этому наблюдению меньше 7 суток (`stale_after_days`); ровно 7 суток — цена уже не актуальна.

Неизвестное наличие при найденной цене считается наличием: магазин цену показал. Сбои проверки после последнего успешного наблюдения показываются с причиной, но цену не убирают, пока ей меньше 7 суток.

**Статус цены товара.** Если хоть одна ссылка участвует — `ok`; если последняя проверка лучшей ссылки не удалась — `check_failed`, цена при этом показывается. Если не участвует ни одна, статус выбирается по порядку: `no_links` — у товара нет привязанных ссылок; `out_of_stock` — хоть одна свежая проверка сказала «нет в наличии»; `stale` — есть только устаревшие цены; `store_disabled` — цены только у выключенных магазинов; `awaiting_check` — успешных проверок ещё не было.

**Лучшая цена товара** — минимум действующих цен участвующих ссылок.

**Итог** — сумма `лучшая цена × quantity` по товарам с `in_total = true`.

Особые случаи:

| Ситуация | На экране | В итоге |
|---|---|---|
| Проверка не удалась, цене меньше 7 суток | Последняя цена, дата и причина сбоя | Учитывается |
| Последней успешной цене 7 суток и больше | Цена с пометкой «не актуальна» и призыв обновить или заменить ссылку | Выходит из итога; отметка «в итоге» показана снятой. Пользователь может включить её снова (`include_stale`) — тогда последняя цена учитывается с предупреждением «цена не актуальна» |
| Товара нет ни в одном магазине | «Нет в наличии» вместо цены | Не учитывается |
| Магазин отключён администратором | Последняя цена с пометкой «магазин отключён»; ссылка не проверяется, новые ссылки на магазин не добавляются | Не учитывается; после включения всё возвращается |
| Изменение ждёт решения | Последняя подтверждённая цена и блок «на проверке» | Учитывается подтверждённая |
| Товар ожидает первой проверки, цены ещё нет | «Ожидает проверки» вместо цены | Не учитывается |
| У товара не осталось ни одной ссылки (все отключены) | Товар остаётся со всей историей и пометкой «Нет ссылок на магазины — добавьте ссылку» | Не учитывается |

**Товар никогда не удаляется автоматически.** Ни устаревание цены, ни отключение последней ссылки не убирают товар из списка и не стирают его историю: он только выходит из итога и показывает, что сделать — обновить, заменить или добавить ссылку. Удалить товар может только пользователь.

**Покупка и архив.** Купленный (`purchased`) и архивный (`archived`) товар не входит в итог, изменения и сводные панели и не удаляется: история сохраняется, вернуть в список можно в любой момент. Ссылки купленного товара проверяются ещё 14 суток после покупки — если цена опустится ниже цены покупки, на карточке видно «сейчас дешевле на …»; потом и у архивного товара ссылки не проверяются, если их не отслеживают активные товары других пользователей.

Статистика покупок: потрачено — сумма `purchase_price_minor × purchase_quantity` за период и по категориям; экономия — разница между самой выгодной ценой среди магазинов в момент добавления товара (первая подтверждённая проверка после добавления) и ценой покупки, умноженная на количество, со знаком (отрицательная — переплата).

Переходы: в списке → куплен, в списке → в архиве и обратно «Вернуть в список»; купленный товар попадает в архив только через список. Покупка: цена за штуку от 1 копейки до 10 млрд ₽, количество 1–999, магазин можно не указывать, дата не позже текущего момента. Ровно через 14 суток после покупки ссылки уже не проверяются. «Сейчас дешевле на …» — разница за штуку с актуальной ценой. Периоды статистики те же, что у изменения итога: сутки, 7, 30 и 365 суток от 00:00 по Москве. Если цены в момент добавления не было, покупка входит в «потрачено», но не в экономию.

**История цены товара непрерывна.** Она складывается из наблюдений всех его ссылок за время их привязки к товару (`item_links.valid_from` … `valid_to`). Привязка действует на отрезке `[valid_from, valid_to)`. Цена товара на момент берётся по ссылкам, привязанным в этот момент, с учётом всех их наблюдений до него: ссылка общая, и её уже известная цена видна сразу после привязки. Минимум периода берёт только наблюдения, сделанные за время привязки. Новая или заменённая ссылка продолжает историю, а не начинает её заново: если ссылка того же магазина, график этого магазина продолжается одной линией; лучшая цена и график суммы на каждый день берутся по ссылкам, привязанным к товару в тот день.

**Сутки** начинаются в 00:00 по Москве. Изменение за сутки — текущая цена против последней подтверждённой до 00:00 сегодня. За неделю, месяц и год — против последней подтверждённой до 00:00 семь, тридцать и триста шестьдесят пять суток назад. Если более ранней цены нет, изменение не показывается. Изменение итога считается только по товарам, у которых цена учтена в обоих моментах, — новый товар или товар, только получивший цену, не выдаётся за подорожание; процент — от прежней суммы этих же товаров.

**Минимум периода** — самая низкая подтверждённая действующая цена товара за одну штуку среди всех его магазинов за выбранный период (сутки, неделя, месяц, год). API отдаёт `period_min_minor`, `period_min_text`, `period_min_date` и `period_min_store`. Если подтверждённых цен за период нет, поля равны `null`.

**Графики цены** строятся по каждому магазину отдельно и показывают цену за одну штуку. Количество на них не влияет. Точка — цена на конец московского дня (сегодня — на текущий момент); неделя, месяц и год — 7, 30 и 365 точек. День без цены — `no_data`, с устаревшей ценой — `stale`, оба без значения. График магазина — его собственная история, поэтому выключение магазина точки не прячет. Если ни в одной точке нет значения, график пуст.

**График суммы** категории и общего итога считается из истории цен за штуку по сегодняшнему составу списка: текущим количествам и отметкам «в итоге». Он отвечает на вопрос «сколько стоил бы нынешний список в прошлые дни». Цены каждого дня берутся по правилам итога; выключенный магазин не учитывается и в прошлом, а после включения его цены возвращаются. Снимки сумм не хранятся.

**Подозрительное изменение** (пороги в настройках администратора):

- название отличается от эталонного больше чем на 15 % (схожесть нормализованных строк ниже 85 %);
- цена отличается от последней подтверждённой больше чем на 30 %.

Ровно на пороге — не подозрительно. Названия нормализуются как имена (регистр, «ё», пробелы), цена сравнивается действующая (по карте, если есть). Нет эталонного названия, прежней цены или новой цены (нет в наличии) — сравнивать не с чем, изменение не подозрительно. Проверка без цены ценовое подозрение не закрывает.

Пока решение не принято, новые наблюдения сохраняются как неподтверждённые, в статистике остаётся последняя подтверждённая цена. Решение принимает администратор, потому что ссылка общая: принять новое значение, отклонить его, заменить ссылку, отключить ссылку или — при скачке цены — перепроверить сейчас. Отключение ссылки закрывает её связь со всеми товарами (`item_links.valid_to`): товары остаются в списках с другими магазинами, ссылка больше не проверяется. Перепроверка — это срочное задание вида `on_add` на одну ссылку (раздел 8), а не ручной запуск всей проверки; её результат оценивается теми же правилами и, если цена снова за порогом, остаётся на решении. Если следующая проверка вернула цену в пределах порога, ценовое подозрение закрывается автоматически с записью в аудит.

## 7. Сбор цен

Контракт `StoreParser` принимает нормализованный URL и контекст проверки, возвращает `ParsedProduct` или типизированную ошибку. Результат: название, цена, цена по карте, наличие, адрес фото, валюта, подтверждённый регион.

1. Registry определяет магазин по нормализованному hostname.
2. Для подключённого магазина запускается его адаптер. Каждый магазин — отдельный файл в `parsers/stores/`, образцы его страниц — в своей папке тестов; адаптеры не импортируют друг друга (контракт import-linter). Добавить магазин — новый файл, строка в реестре, образцы и контрактные тесты.
3. Для сайта без адаптера запускается общий парсер. Сначала быстрый запрос; если сайт защищён или цены нет — браузер. Источники по очереди: данные сайта (JSON-LD → Open Graph и meta → микроразметка), затем цена «глазами»: самый крупный незачёркнутый ценник рядом с заголовком, без «в месяц», рассрочки, бонусов и блоков внизу страницы; наличие — по кнопкам «В корзину» и «Нет в наличии». Подход — из рабочего парсера владельца. Способ, который сработал для сайта, запоминается.
4. Решение владельца (06.10.2026): ссылку на любой сайт добавляет любой пользователь, магазин создаётся сам (название — `og:site_name` или имя сайта), цена видна сразу, без подтверждения администратором. Взамен: у цены показан источник («данные сайта» или «найдено на странице»), расхождение данных сайта и цены «глазами» больше 3 % пишется в заметки, правила подозрительных изменений (раздел 6) действуют как обычно, администратор может отключить сайт или ссылку.

### Доступ к страницам

Парсер поднимается по ступеням и останавливается на первой сработавшей:

1. Обычный HTTPS-запрос и структурированные данные страницы.
2. Открытые JSON-запросы, которыми пользуется сама страница магазина.
3. Настоящий браузер с постоянным профилем на домашнем IP, с выставленным городом и паузами. Если магазин пускает к JSON только с cookies после проверки в браузере (Ozon, DNS), браузер открывается редко — чтобы получить cookies, — а товары проверяются быстрыми запросами ступени 2 с этими cookies.
4. Если магазин показал CAPTCHA, домен ставится на паузу и проверка повторяется через 15 секунд, затем через 60 секунд. Если CAPTCHA осталась, домен отдыхает до следующего запуска, а администратор получает уведомление и может пройти её вручную в профиле браузера worker.

В план не входят сервисы автоматического решения CAPTCHA и покупные прокси: они нарушают правила магазинов и приводят к блокировке домашнего IP.

Wildberries (06.10.2026): страница товара открывается в браузере; из собственного запроса сайта берутся его служебные заголовки (без cookies), город и `dest` называет геосервис Wildberries — это и есть подтверждение региона, — затем JSON карточки запрашивается изнутри страницы с `dest` Санкт-Петербурга. Без выбранного адреса страница сама берёт Москву, а цены в Санкт-Петербурге другие. В один запрос помещается до 100 артикулов.

DNS (06.10.2026): только браузер (Qrator); город DNS выбирает по IP и хранит в подписанной cookie, подтверждение — `cityGuid` в настройках страницы; цена — из JSON `/product/microdata/<id>/`, который запрашивает сама страница (запись schema.org Product).

Ozon (06.10.2026): только браузер; JSON-LD на карточке нет, цены — из виджета цены парами «сумма — подпись»: «С банками» (картой Ozon Банка и партнёров) — цена по карте, «С другими банками» — обычная; город — `location.current.city` в настройках страницы; наличие — по кнопке корзины. Закончившийся товар Ozon перенаправляет на поиск с виджетом `webOutOfStock`: название и фото берутся из виджета, а не из страницы поиска.

Яндекс Маркет (06.10.2026): карточка отдаётся быстрым запросом, при капче — браузер; регион Маркет выбирает по IP (cookie `yandex_gid` не учитывает), подтверждение — `region.id` в данных страницы (2 — Санкт-Петербург); цена в JSON-LD — с картой Яндекс Пэй, обе цены — в блоке `priceDetails` («без карты» — обычная, «Пэй» — по карте); снятый с продажи товар — `isNotOnSale`.

Авито (06.10.2026): только браузер, и только с профилем, в котором администратор хотя бы раз прошёл проверку вручную — без этого 429 и капча с первого запроса; проверять редко и с паузами. Цена — из JSON-LD объявления; регион не подтверждается: цену назначил продавец, от города смотрящего она не зависит. Снятое объявление (проверено на настоящей странице): JSON-LD остаётся с OutOfStock, на странице «Объявление снято с публикации.» — надпись важнее данных для поисковиков.

Регард (06.10.2026): без браузера, город — cookie `city_id` (Санкт-Петербург — 137), подтверждение — `town.cookieTownId` в состоянии страницы (`__NEXT_DATA__`); цена — общим парсером из JSON-LD. Общий парсер не читает товары, вложенные в товар (похожие, сопутствующие), и не смешивает источники: цена из JSON-LD не перебивается микроразметкой рекомендаций.

Ограничения:

- Один домен — одна проверка одновременно, пауза задаётся `min_delay_ms`. Разные домены идут параллельно с общим лимитом.
- После `403` или `429` домен отдыхает с нарастающей паузой: 15 минут, 1 час, до следующего планового запуска. Для CAPTCHA паузы короче, см. ступень 4.
- Задания поставленного на паузу домена остаются в очереди и не считаются ошибкой, пока паузы не исчерпаны.
- Таймауты, размер ответа, число перенаправлений и время браузера ограничены.

### Защита от SSRF

Worker стоит в домашней сети рядом с NAS и роутером, поэтому это главный риск.

- Разрешена только схема `https`. Запрещены адреса с логином и паролем, нестандартные порты, IP вместо имени.
- Пользователь добавляет ссылку на любой сайт; сайт, отключённый администратором, даёт `STORE_NOT_ALLOWED` («Этот сайт отключён администратором»). Браузер worker открывает любые сайты пользователей, поэтому: у каждого сайта свой профиль, скачивание файлов запрещено, лимит — 20 новых ссылок в час на пользователя.
- Имя разрешается один раз, адрес проверяется и закрепляется на время запроса; так закрывается DNS rebinding. Каждое перенаправление проверяется заново.
- Контейнер worker работает в отдельной сети Docker. Правила межсетевого экрана узла запрещают ему приватные, локальные и служебные диапазоны; разрешены только интернет и адрес API. К PostgreSQL и туннелю у него доступа нет, хотя они на том же узле.
- Браузер ходит в сеть только через проверяющий прокси worker (`--proxy-server`, петлевые адреса тоже): пропускается лишь `CONNECT имя:443` с публичными адресами, прокси сам разрешает имя и соединяется с проверенным адресом. Так проверяются подресурсы, перенаправления, всплывающие окна и WebSocket; перехват запросов Playwright шаги перенаправлений не видит (проверено 06.10.2026). QUIC и прямой UDP у WebRTC отключены.
- Пользователь не задаёт заголовки, прокси, JavaScript и селекторы.

### Картинки

Worker скачивает фото товара: не больше 2 МБ, только JPEG, PNG, WebP. Файл перекодируется и передаётся на сервер, сайт отдаёт его со своего домена. Ссылки на CDN магазинов клиентам не отдаются.

### Новый магазин

1. Найти готовые реализации (см. `AGENTS.md`, раздел про GitHub) и согласовать подход.
2. Добавить модуль адаптера, регистрацию домена, сохранённые образцы страниц без cookies и личных данных.
3. Контрактные тесты: цена, цена по карте, наличие, не найдено, CAPTCHA, изменившаяся разметка, чужой регион.
4. Включить магазин (`enabled`) только после зелёных тестов.

## 8. Очередь, запуски, расписание

Запуск (`parse_runs`) состоит из заданий (`check_tasks`), одно задание — одна ссылка.

Гарантии на уровне базы:

- Частичный уникальный индекс: не больше одного активного запуска вида `scheduled` или `manual`.
- Частичный уникальный индекс: не больше одного активного задания на ссылку.
- `slot_key` (например `2026-10-05T09:00`) уникален: плановый запуск не создастся дважды даже при двух процессах планировщика.
- `price_observations.task_id` уникален: повтор результата не создаёт вторую строку истории.

Поведение:

- Второй администратор нажал «Запустить» во время проверки — получает `409 RUN_IN_PROGRESS` и текущий прогресс. Кнопка заменяется индикатором: «Идёт проверка: 42 из 130».
- Наступило плановое время при активном запуске — новый запуск не создаётся, пропуск записывается в журнал.
- Сервер был выключен в плановое время — после старта выполняется один пропущенный запуск за текущие сутки.
- Worker берёт задания запросом `FOR UPDATE SKIP LOCKED`, получает аренду на 2 минуты и продлевает её heartbeat. Истёкшая аренда возвращает задание в очередь; после 3 попыток задание закрывается с ошибкой.
- Остановка запуска администратором: новые задания не выдаются, текущие дорабатывают.
- Ссылки отключённого магазина в запуск не попадают.

Расписание: по умолчанию одна проверка в 09:00 по Москве. Администратор меняет время и добавляет вторую и третью проверку в настройках.

Устройство (срез 6.5):

- Планировщик — отдельный процесс `python -m pricewatch.bootstrap scheduler`. Каждые 30 секунд он возвращает просроченные задания и запускает наступивший слот. Сразу после старта берётся промежуток от 00:00 текущих суток: так выполняется один пропущенный запуск. Сбой обхода пишется в журнал, слот запускается на следующем удачном обходе.
- Времена проверок хранятся в настройке `check_times` списком «ЧЧ:ММ». Неверное значение — ошибка в журнале, а не тихая замена на 09:00.
- В запуск попадают ссылки действующих привязок товаров «в списке» и купленных меньше 14 суток назад, у включённых магазинов и незаблокированных пользователей. Общая ссылка — одно задание. Ссылка, у которой уже есть активное задание (например, срочное), второй раз не ставится. Пустой запуск сразу завершён.
- Запуск завершается, когда у него не осталось ждущих и выданных заданий. Остановленный запуск сначала получает статус `stopping`, а когда выданные задания доработают — `finished`.
- После третьей истёкшей аренды задание закрывается с `TIMEOUT`, и эта ошибка попадает в историю ссылки. Задание остановленного запуска при истёкшей аренде отменяется.
- Запустить и остановить запуск может только действующий администратор. Срочный запуск `on_add` не останавливается и не мешает плановому и ручному.

### Добавление товара

1. Ссылка уже есть в каталоге, и её цене меньше суток — товар сразу получает цену, парсер не запускается.
2. Иначе создаётся срочное задание вида `on_add` на одну ссылку. Интерфейс показывает «проверяется».
3. Результат пришёл за 60 секунд — цена появляется сразу.
4. Worker недоступен или не успел — товар сохраняется без цены со статусом «ожидает проверки» и подхватывается ближайшим плановым запуском.

В запуски попадают только ссылки активных товаров и товаров, купленных меньше 14 суток назад. Это не ручной запуск парсера: проверяется одна ссылка. Лимит — 20 новых ссылок в час на пользователя. То же срочное задание на одну ссылку ставит кнопка администратора «Перепроверить сейчас» у подозрительного скачка цены.

### Протокол worker

- `POST /worker/v1/claim`, `/heartbeat`, `/result`, `/image`.
- Токен worker — 32 случайных байта, в базе хеш. При ротации одновременно действуют старый и новый токен, пока worker не перешёл на новый. Выпуск и смена — командами `create-worker` и `rotate-worker-token`, токен печатается один раз.
- Одновременно выдаётся не больше одного задания на магазин: при выдаче блокируется и строка магазина, поэтому второй worker пропускает его задания.
- Результат worker — недоверенный ввод: схема Pydantic, диапазоны цен, длины строк, допустимые статусы. Результат по чужому или истёкшему заданию отклоняется.
- Процесс worker — `python -m pricewatch.worker`, настройки `PRICEWATCH_WORKER_*` и `worker.env` (образец `worker.env.example`). Цикл: взять задание → выдержать паузу магазина (у браузерных магазинов к ней добавляются случайные 0–4 с) → проверить → отправить результат. Пока идёт проверка, аренда продлевается каждые 30 с. Неожиданная ошибка парсера пишется в журнал и уходит как `INTERNAL_ERROR`, worker продолжает работу. Сервер не принял токен — worker останавливается с кодом 4. Сигнал остановки дожидается конца текущей проверки.

## 9. API и сайт

- `/api/v1` — JSON для приложения, описан в `openapi/v1.yaml`. Контракт пишется до клиентов; при расхождении с этим разделом прав контракт.
- Статусы в ответах — открытые строки: клиент показывает нейтральное состояние для неизвестного значения.
- Цвет магазина передаётся номером палитры (`store-1` … `store-8`); значение цвета клиент берёт из своих токенов под текущую тему.
- `/web` — страницы и HTML-фрагменты для сайта. Те же сценарии application layer, другой формат ответа.
- Суммы приходят числом копеек и готовой строкой для показа (`price_minor`, `price_text`). Форматирование денег живёт в одном месте — на сервере.
- Вид чисел: разряды — узкий неразрывный пробел, перед «₽» — неразрывный пробел («12 990 ₽»); копейки только ненулевые («12 990,50 ₽»); минус — знак «−», рост — «+»; процент всегда с одним знаком после запятой («0,0%», «1,0%»), половины округляются вверх.
- Данные графиков: упорядоченный массив `{date, value_minor, label, status}`.
- Списки — с пагинацией и стабильной сортировкой.
- Новое необязательное поле не ломает старый клиент. Удаление и переименование — только в `/api/v2`.
- Изменяющие запросы требуют аутентификации, проверки владельца, валидации на сервере, версии записи и ключа идемпотентности.
- Непроверенные данные не вкладываются в исполняемый inline JavaScript.

## 10. Ошибки, логи, уведомления

Ошибки не маскируются нулевой ценой, пустым успешным ответом или заглушкой. Коды: `INVALID_URL`, `STORE_NOT_ALLOWED`, `BLOCKED`, `CAPTCHA`, `TIMEOUT`, `LAYOUT_CHANGED`, `PRICE_NOT_FOUND`, `REGION_MISMATCH`, `UNSUPPORTED_CURRENCY`, `WORKER_OFFLINE`, `RUN_IN_PROGRESS`, `VERSION_CONFLICT`, `DB_ERROR`, `INTERNAL_ERROR`.

Коды API и входа: `AUTH_REQUIRED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_ERROR`, `RATE_LIMITED`, `PAIRING_CODE_INVALID`, `PAIRING_CODE_EXPIRED`, `REFRESH_TOKEN_INVALID`, `REFRESH_TOKEN_REUSED`, `IDEMPOTENCY_KEY_REUSED`, `NAME_TAKEN`, `INVALID_CREDENTIALS`, `INVITE_INVALID`, `LOGIN_TAKEN`, `CSRF_FAILED`.

- Каждая попытка сохраняет статус, время, внутренние идентификаторы, краткое безопасное сообщение и correlation ID.
- Полный traceback пишется в журнал узла. Токены, cookie, заголовки авторизации и чувствительные параметры URL вырезаются.
- Неожиданное исключение на любой границе ловит верхний обработчик: запись в журнал и уведомление администраторам. Пустой `except` и молчаливый запасной путь запрещены.
- Уведомления создаются строкой в `notifications` в той же транзакции, что и событие. Бот забирает Telegram-уведомления через `/internal/v1`. Сбой Telegram не откатывает данные и не останавливает парсер.
- Пользователь получает только сводку проверки: после завершения запуска вида `scheduled` или `manual` каждому пользователю с привязанным Telegram уходит одно сообщение «Проверка завершена: изменения есть» или «Проверка завершена: изменений нет». Изменение — подтверждённая смена действующей цены или наличия хотя бы одного его товара относительно предыдущего подтверждённого наблюдения. Список товаров в сообщение не входит. Запуск `on_add` сводку не создаёт. Отдельных уведомлений о цене, наличии и устаревании нет.
- Системные уведомления администраторов уходят в два канала: Telegram и колокольчик на сайте и в приложении со счётчиком непрочитанных. Колокольчик есть только у администраторов: если бот недоступен, предупреждение доходит через него. Push появится после покупки Apple Developer Program.
- Одинаковый инцидент склеивается по `dedup_key`: одно сообщение, счётчик повторов, сообщение о восстановлении.
- Пользователь видит короткое описание и идентификатор ошибки, никогда traceback.
- Ошибка одной ссылки не останавливает остальные.

### Отчёты об ошибках приложения

`POST /api/v1/client_errors` принимает отчёт о неожиданной ошибке iOS-приложения.

- Только с bearer-токеном. Ошибки до входа остаются в системном журнале устройства.
- Тело: `app_version`, `os_version`, `screen`, `error_code`, `message` (до 2000 символов), `occurred_at`. Лишние поля отклоняются.
- Отчёт — недоверенный ввод: текст нигде не выводится как HTML, из него вырезаются токены и параметры URL.
- Лимит — 20 отчётов в час на устройство; сверх лимита ответ `429`, приложение отчёт не повторяет.
- Ответ содержит `error_id`, который приложение показывает пользователю.
- Администраторы получают уведомление; одинаковые ошибки одной версии склеиваются по `dedup_key`.
- Отчёты хранятся 90 суток.
- Сбой отправки отчёта не показывается пользователю и не порождает новый отчёт.

Кому что приходит:

| Событие | Кому | Каналы |
|---|---|---|
| Проверка завершена: изменения есть / нет | Каждому пользователю с привязанным Telegram | Telegram |
| Подозрительное изменение, CAPTCHA, сбой запуска, worker или бот недоступен, неожиданное исключение, отзыв семьи refresh-токенов, отчёт об ошибке приложения, сбой копии | Администраторам | Telegram и колокольчик |

## 11. Резервные копии

- Ежедневный зашифрованный дамп базы и каталога картинок на домашнем узле, на отдельном от базы диске. Хранится 30 суток.
- Та же зашифрованная копия отправляется на арендный хост и хранится там 30 суток; ключ шифрования на хост не попадает. Иначе отказ диска Raspberry Pi уничтожит и базу, и копии.
- Выгрузка на NAS реализована и покрыта тестами, но выключена флагом `BACKUP_NAS_ENABLED=false` до покупки NAS.
- Ключ шифрования хранится отдельно от копий.
- Неудачная копия и копия старше 36 часов дают уведомление администраторам.
- Восстановление на чистый узел проверяется при деплое и затем раз в квартал.

## 12. Этапы

Этап закрыт, когда его проверки зелёные и `FEATURE_STATUS.md` обновлён.

**0. Контракты.** Владелец кладёт образец дизайна в `design_reference/` (структура — в `AGENTS.md`). Из него выписать токены дизайна (цвета, шрифты, отступы, радиусы, тени) в CSS-переменные и согласовать их с владельцем. Описать OpenAPI. Создать `PROJECT_MAP.md`, контракты import-linter, `tools/`. Проверки: карта проходит `check_project_map.py`; секретов во frontend нет.

**1. Каркас и безопасность.** Конфигурация, типизированные ошибки, логи, HTTPS, заголовки безопасности. Проверки: секреты не попадают в Git и ответы.

**2. База.** Миграции, репозитории, ограничения из раздела 5. Проверки: миграция вверх и вниз, параллельные обновления, конфликт версии, фильтр по владельцу.

**3. Пользователи и вход.** Приглашения, сессии, pairing, refresh, роли. Проверки: перебор пароля и кода, повтор refresh внутри и вне окна, CSRF, запрос с cookie и bearer одновременно, доступ к чужим идентификаторам, действия администратора от обычного пользователя.

**4. Доменные правила.** Раздел 6 целиком. Проверки: unit-тесты граничных значений — ровно 7 суток, ровно 15 % и 30 %, граница 00:00, товар без наличия, цена по карте, смена количества.

**5. Парсер.** Интерфейс, registry, нормализаторы, безопасная загрузка, общий парсер, браузерная загрузка (patchright, Chrome, проверяющий прокси), первый адаптер (Wildberries — по JSON, который запрашивает сама страница), Регард — общим парсером без браузера. Проверки: SSRF (приватные адреса, перенаправления, rebinding, все запросы браузера), огромный ответ, таймаут, изменившаяся разметка, чужой регион. Загрузка фото — отдельным срезом. Порядок магазинов после Wildberries: Регард, Ozon, DNS, AliExpress, Технопарк, Авито — у каждого сначала проверяется путь без браузера (06.10.2026 без браузера открывается только Регард).

**6. Очередь и расписание.** Раздел 8. Проверки: два одновременных ручных запуска, ручной поверх планового, два планировщика, обрыв worker, повтор результата, добавление одной ссылки двумя пользователями одновременно, добавление при выключенном worker.

**7. API и сайт.** Эндпоинты по одному модулю, фрагменты, настройки администратора. Проверки: XSS, подмена цены и количества, неверные типы и размеры, шаблоны на пустой базе, одной записи и большом списке.

**8. Бот и сторож.** Раздел 1 и 10. Проверки: Telegram недоступен, API недоступен, worker молчит, бот молчит, повтор одного инцидента, два экземпляра бота.

**9. Интерфейс.** Все страницы на телефоне и десктопе, клавиатура, скринридер, reduced motion. Сравнение со снимками эталона.

**10. iOS.** См. `IOS_APP_PLAN.md`. Проверки эндпоинта отчётов: без токена, превышение лимита, слишком длинный текст, лишние поля, токен внутри текста.

**11. Деплой и восстановление.** Compose с лимитами под память Raspberry Pi, туннель и пересылка порта на арендном хосте, Caddy дома, healthcheck, ротация логов, копии, проверка восстановления. Проверки: обрыв туннеля и его восстановление, перезагрузка Raspberry Pi, сайт недоступен в обход арендного хоста, на хосте нет закрытого ключа сертификата, IP посетителя доходит до API, подделанный PROXY-заголовок извне отклоняется, переезд на второй хост без правок на Raspberry Pi.

## 13. Правила готовности

- Ни один сценарий не отвечает «успешно», если операция не выполнена.
- Любой отказ имеет явный тип, запись в журнал и понятный результат на экране.
- Повторы безопасны.
- Функция включается только с тестами, миграциями, логированием и проверкой прав.
- `PROJECT_MAP.md` и `FEATURE_STATUS.md` обновлены в той же задаче.

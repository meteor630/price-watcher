# Price Watcher — план приложения для iPhone и iPad

## Цель

Сделать единое нативное приложение для iPhone и iPad. Оно показывает те же товары, категории, цены и историю, что сайт. Все данные и правила принадлежат backend; приложение — ещё один клиент этого backend, а не отдельная система.

## Технологии

- **Swift 6 + SwiftUI** — интерфейс и общие компоненты под iOS/iPadOS.
- **URLSession + async/await** — HTTPS-запросы к `/api/v1`.
- **Swift Charts** — графики цен и итогов.
- **Keychain** — одноразовый refresh-токен/сессия. Не хранить токен в UserDefaults и не вшивать секреты в приложение.
- **SwiftData** — только необязательный локальный кэш для чтения без сети; сервер остаётся источником истины.
- **XCTest** — unit, API contract и UI-тесты.
- **Установка через Xcode по кабелю** с бесплатной учётной записью Apple. Ограничения: сборка работает 7 дней и затем переустанавливается; push-уведомления и Universal Links недоступны. TestFlight и подписание в CI — после покупки Apple Developer Program.

## Как приложение общается с сайтом и сервером

1. iPhone/iPad обращается к общему версионируемому JSON API `https://домен/api/v1`.
2. Сайт использует тот же слой бизнес-сценариев. Приложение не обращается напрямую к PostgreSQL, не знает файловую структуру сервера и не парсит сайты магазинов.
3. Перед началом SwiftUI-разработки зафиксировать OpenAPI-схемы и примеры ответов. Swift-модели генерируются из OpenAPI; способ генерации выбирается сравнением готовых решений по `AGENTS.md`. Добавить contract-тесты.
4. API-ответы содержат нормализованные сущности и статусы, например `price_minor`, `price_text`, `card_price_minor`, `availability`, `checked_at`, `status`, `change`, `history`, `version`. Имена в JSON — `snake_case`; декодер переводит их в свойства Swift автоматически. Суммы — целые копейки (`Int`) и готовая строка для показа; `Double` не используется, приложение деньги не форматирует.
5. API имеет совместимые изменения: новые необязательные поля старый клиент игнорирует; несовместимое изменение делается в `/api/v2` после миграционного периода.
6. Вход — по pairing-коду, который сервер выдаёт по кнопке на сайте или по команде боту в Telegram: 8 символов, 5 минут, одноразовый; неверные вводы ограничены по IP. Код вводится вручную. Сервер меняет его на access-токен (15 минут) и ротируемый refresh-токен (60 дней). Refresh хранится в Keychain, access — в памяти. Обновление токена выполняется одним запросом одновременно; при обрыве сети запрос повторяется с тем же refresh — сервер в течение 60 секунд вернёт ту же новую пару. Выход отзывает устройство на сервере.
7. Все изменяющие запросы проверяются backend по владельцу записи, несут версию записи и idempotency key. Ответ `409 VERSION_CONFLICT` содержит актуальное состояние: приложение показывает его и сообщение о конфликте.
8. Токен Telegram-бота, ключ worker, ключи базы и серверные секреты никогда не попадают в приложение.

## Страницы и возможности приложения

### Вход и подключение

- Поле ввода одноразового кода, полученного на сайте или от бота.
- Состояния: ожидание кода, подтверждение, ошибка/истечение кода, успешный вход.
- При истечении сессии приложение предлагает войти снова и не зацикливает запросы.

### Главная

- Общий итог покупок и изменение за сутки/неделю/месяц/год.
- Карточки категорий с суммой, изменением и небольшим графиком.
- Сводные списки отслеживаемых, подешевевших, подорожавших и отсутствующих товаров.
- Предупреждения о карточке с подозрительным названием или ценой — только администратору.
- Состояние последней проверки и её прогресс, если она идёт. Ручной запуск виден только администратору; при идущей проверке вместо кнопки показан прогресс.
- Системные предупреждения администратору (бот или worker недоступен) — в колокольчике.
- Сохранить порядок категорий на сервере. Перетаскивание поддержать жестом; предложить доступный путь через кнопки «выше/ниже».

### Категория

- Сумма категории и период изменения.
- Товары в группах: отметить «в итоге», изменить количество, перейти в карточку, посмотреть магазины.
- Цена по карте и обычная цена отображаются отдельно.
- История общей стоимости категории с перекрестием/подсказкой по дате.
- Изменение порядка категорий и товаров выполняется через backend и отображает процесс сохранения.

### Товар

- Название, фотография, текущая лучшая цена и магазин, наличие, цена без карты.
- Сравнение магазинов и график цены по выбранному магазину за одну штуку; периоды — те, что отдаёт API.
- История событий и ссылка «Открыть в магазине».
- Действия «в итоге», количество и изменение товара.
- Если изменение ждёт решения, показана последняя подтверждённая цена и пометка «на проверке». Блок с решениями видит только администратор.
- Состояния цены: «нет в наличии», «не актуальна», «ожидает проверки», «магазин отключён», последняя цена с причиной сбоя.

### Поиск/список (после MVP)

- Поиск товара по имени и фильтр по категории/магазину/наличию.
- Не добавлять сложные фильтры до проверки основного потока.

### Настройки (после MVP)

- Добавление и редактирование товара/ссылок, категории и группы.
- Настройка расписания и уведомлений только если эти API-функции реально есть.
- Подтверждение перед разрушительными изменениями; «Отменить» 3 секунды после удаления.

## Адаптация под устройство

### iPhone

- Нижняя навигация максимум из 3–4 главных разделов; вторичные страницы открываются через `NavigationStack`.
- Одна основная колонка. Карточки растягиваются на доступную ширину; действия доступны большим пальцем и не требуют точного попадания.
- Фильтры и вторичные действия — в sheet. Формы учитывают клавиатуру и safe areas.
- Длинные названия переносятся; цены не дробятся и не скрывают валюту.

### iPad

- `NavigationSplitView`: боковая навигация/список категорий и основная область.
- Главная и группы используют 2–3 колонки в зависимости от ширины. Страница товара использует две колонки, когда место позволяет.
- Поддержать портретный и альбомный режим, внешнюю клавиатуру, pointer/trackpad и многозадачность Split View.
- Не растягивать карточки на всю ширину при узком окне Split View; сетка перестраивается по фактической ширине окна.

## Структура проекта приложения

```text
ios/PriceWatcher/
  App/                 точка входа, маршруты, конфигурация
  Core/Networking/     APIClient, авторизация, обработка ошибок
  Core/Models/         типизированные API-модели
  Core/Storage/        Keychain и read-only cache
  Core/DesignSystem/   цвета, типографика, кнопки, карточки
  Features/Auth/
  Features/Home/
  Features/Category/
  Features/Product/
  Features/Settings/
  Features/Issues/
  Resources/           локализация, ассеты
  Tests/               unit, contract и UI tests
```

Экран общается с backend через `@Observable` view model/use case; View не вызывает SQL, не считает доменные итоги и не собирает URL вручную. `APIClient` централизует авторизацию, таймауты, decoding, correlation ID и преобразование ошибок.

## План работ и контрольные точки

### Этап A. Контракт до UI

- Утвердить `/api/v1`, OpenAPI, модель сессии, список экранов и поля каждого ответа.
- Создать и заполнить общий корневой `PROJECT_MAP.md` для backend, сайта и приложения.
- Зафиксировать состояния: пусто, загрузка, ошибка, частичный ответ, offline, подозрительная цена.
- Проверки: контрактные примеры валидны; сайт и приложение читают одну модель; секретов в API нет.

### Этап B. Каркас приложения

- Создать SwiftUI-приложение, темы, навигацию iPhone/iPad, сетевой клиент и обработку ошибок.
- Сделать Preview экранами на fixture-данных; fixture не включать в production.
- Проверки: сборка двух платформ, VoiceOver, Dynamic Type, light/dark, безопасная работа при потере сети.

### Этап C. Авторизация и чтение

- Реализовать pairing/login, обновление сессии, logout/revoke.
- Подключить главную, категории, товары, историю и графики в read-only режиме.
- Проверки: истёкший access, истёкший/отозванный refresh, повторная отправка, потеря сети, отсутствие прав на чужой объект.

### Этап D. Изменения данных

- Добавить отметку «в итоге», количество, сортировку и формы товара/категорий.
- Все изменения сначала сервер подтверждает; интерфейс показывает loading/success/failure и не притворяется, что запрос сохранён.
- Проверки: двойное нажатие, отмена, конфликт параллельного изменения через сайт, повтор запроса после timeout и rollback интерфейса.

### Этап E. Безопасность и полировка

- Проверить Keychain, pairing, отсутствие личных данных в логах, ошибки и ссылки внешних магазинов.
- Выполнить UI-тесты iPhone SE/обычный iPhone/iPad portrait/iPad landscape/Split View.
- Проверить доступность, reduced motion, контраст, горизонтальный overflow и очень длинные названия.

### Этап F. Установка и сопровождение

- Устанавливать на устройство из Xcode по кабелю; адрес сервера задаётся конфигурацией сборки, секретов в проекте нет.
- После покупки Apple Developer Program: подписание в CI, внутренний TestFlight, затем push.
- После релиза поддерживать совместимость API минимум с предыдущей версией приложения; при ошибках можно откатить релиз клиента без миграции базы.

## Offline и уведомления

- Offline сначала только read-only: показать дату кэша и явную плашку «Нет связи; данные на …». Не выдавать кэш за свежие цены. Backend остаётся источником истины; кэш перечитывается после каждого успешного ответа сервера.
- Не ставить изменения в невидимую очередь. Если позднее добавить offline-редактирование, показывать каждое ожидающее действие и разрешать конфликт.
- Push через APNs отложен: он требует платной учётной записи Apple. До этого пользователь получает только сводку проверки в Telegram. Колокольчик в приложении есть только у администратора и содержит системные уведомления: список и счётчик непрочитанных обновляются при открытии и обновлении экрана.
- Push должен быть кратким и не раскрывать лишние детали на экране блокировки; предпочтение и типы уведомлений настраиваются пользователем.

## Процесс разработки, тесты и ошибки

Порядок работы, запреты, правила исправления ошибок и тестов — в `AGENTS.md`; они действуют и для приложения.

- Писать unit-тесты на каждую самостоятельную логику приложения: модели/декодирование, форматирование денег и дат, view model/use case, состояния загрузки/ошибки, retry и правила локального read-only кэша. Каждый исправленный дефект закреплять тестом, где это возможно.
- Для API-контрактов использовать contract-тесты; ключевые пользовательские потоки — UI-тестами; Keychain, сессии и offline-кэш — тестами на реальные границы. Не тестировать бессодержательно сам SwiftUI-фреймворк.
- Неожиданные ошибки клиента писать в системный журнал устройства и отправлять на backend запросом `POST /api/v1/client_errors` (описан в `DEVELOPMENT_ARCHITECTURE.md`, раздел 10) без токенов, URL с секретными параметрами и личных данных; backend присваивает идентификатор и уведомляет администраторов. Backend отправляет внутренние исключения и критичные сбои владельцу в Telegram; приложение не содержит Telegram bot token и не посылает туда секреты напрямую.
- Ошибки, ожидаемые пользователем (валидация, отсутствие сети, сессия истекла), отображать понятным способом. Неожиданные ошибки получают идентификатор для поддержки и безопасно логируются; не маскировать их пустым экраном или фиктивным успешным состоянием.

## Границы MVP

В первую версию включить вход, просмотр главной/категории/товара/графиков, обновление данных с сервера и базовые изменения количества/«в итоге». Полные настройки парсинга, сложное редактирование магазина, push и offline-редактирование отложить до стабильного API. Парсер и логика цен остаются только на backend.
